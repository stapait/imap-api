# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

An HTTP API that exposes operations over the IMAP protocol, written in Go (chosen for performance/concurrency — concurrent-safe operations use goroutines). Endpoint design and other specifics are still being worked out — see `api/README.md` for the current draft and stack decisions. `GET /folders` is implemented so far.

## Working agreement

- Always ask before proceeding whenever there's ambiguity or more than one reasonable alternative (e.g. choice of base Docker image, library, or approach). Don't guess silently.
- Markdown files: don't hard-wrap lines at column 80 (or any column) — write each paragraph/list item as a single line, no matter how long.

## Repository layout

- `README.md` — high-level project overview. Can be technical at a beginner/superficial level (e.g. a one-line-per-endpoint list of what the API does), but no implementation detail (params, response shapes, encoding rules, auth mechanics, open design questions) — that belongs in `api/README.md` during design, and in the Swagger/OpenAPI spec once the API is implemented.
- `api/` — the Go API project. `cmd/server` (entrypoint) + `internal/` (config, IMAP client, HTTP handlers) + `config/config.<env>.yaml` + `test/integration/` (integration tests, one per endpoint, gated behind the `integration` build tag) + `Taskfile.yml` (`task test:unit`, `task test:integration`). See its own `README.md` for stack decisions, endpoint draft, and open questions.
- `docker/` — local development infrastructure.
  - `docker-compose.yml` — runs Dovecot for local IMAP testing.
  - `dovecot/conf.d/` — Dovecot config drop-ins mounted individually into the image's `/etc/dovecot/conf.d/` (mount files individually, not the whole directory — the `dovecot/dovecot` image ships its own default conf.d files there, e.g. `auth.conf`, which wires up the `USER_PASSWORD`-based auth; bind-mounting the whole directory would hide them and break auth).
  - `.env.example` — copy to `.env` to override `DOVECOT_MAILBOX_PASSWORD`.
  - `generate-emails/` — scripts that generate the raw `.eml` test-data pool (see below and its own README.md).
    - `emails-generated/` — flat output of the `generate-emails/` scripts (gitignored).
  - `populate-mailbox/` — script that delivers curated fixtures into the local Dovecot (see below and its own README.md).
  - `emails/` — manually organized `.eml` fixtures, one subfolder per IMAP folder (gitignored, populated by hand from `generate-emails/emails-generated/`).
  - `emails-permanent/` — manually added `.eml` fixtures meant to persist forever: **not** gitignored (versioned in git) and never wiped/regenerated by any script, unlike `emails/`. Always flat (no subfolders) — every file here is delivered straight to INBOX.

## Local Dovecot (docker/)

- Image: `dovecot/dovecot:latest` (official image maintained by the Dovecot project).
- No TLS: connections are plain/local-only by design (`ssl = no`, `auth_allow_cleartext = yes` in `zz-local-plain.conf`). Don't reintroduce SSL requirements without checking with the user first.
- Auth: Dovecot's default `passdb static` accepts **any username** as long as the password matches `USER_PASSWORD`/`DOVECOT_MAILBOX_PASSWORD`. There is no per-user allowlist. If a specific fixed username needs to be enforced later, that requires a custom passwd-file mounted in — ask before adding that complexity.
- Default ports: host `127.0.0.1:143` → container `31143` (plain IMAP); host `127.0.0.1:24` → container `31025` (plain LMTP, used by `populate-mailbox/populate_mailbox.py` to deliver test fixtures — see below).
- `docker/dovecot/conf.d/zz-local-lmtp.conf` enables the plain LMTP listener and sets `auth_username_format = %n` — without it, LMTP (which resolves the user from the full `user@domain` recipient address) and IMAP (which logs in with the bare username) would land in two separate mail stores for what's supposed to be the same test user. It also sets `lmtp_save_to_detail_mailbox = yes` + `recipient_delimiter = +`, which is how `populate_mailbox.py` routes a delivery to a specific folder (`testuser+FolderName@...`) — the target folder must already exist (via IMAP CREATE) before the LMTP delivery, or Dovecot silently falls back to INBOX.

## API tests (api/test/integration/)

- Run via `task test:integration` in `api/` (needs `task` — `go install github.com/go-task/task/v3/cmd/task@latest`, then `$(go env GOPATH)/bin` on PATH). Runs `go test -tags=integration -count=1 ./test/integration/...` — `-count=1` is required, since Go's test cache would otherwise hide a real failure behind a stale "(cached)" pass when nothing in the Go code changed but the external environment (Dovecot) did.
- `TestMain` (in `main_test.go`) enforces preconditions before any test runs: checks the configured IMAP host:port is reachable (fails fast with a `docker compose up -d` hint if not), checks `docker/emails/` has at least one `.eml` (fails with a clear message if not), then always runs `docker/populate-mailbox/populate_mailbox.py` to reset+repopulate the test mailbox — so these tests are destructive to whatever's currently in the local Dovecot's test mailbox.
- One test file per endpoint (e.g. `folders_test.go`), exercising the real HTTP handler via `httptest.NewServer` on top of the real local Dovecot — not mocked. Add a new test file here for each new endpoint.
- **Smoke test requirement:** every endpoint that operates on a specific message (`{pasta}/{uid}`, or similar) must include a smoke test that iterates every real message currently in the test mailbox and asserts the endpoint never errors on any of them — see `smoke_test.go`'s `allFolderEmailRefs`/`runSmokeTest` helpers and `email_test.go`'s `TestGetEmail_SmokeAllMessages` for the pattern to follow. This is how the deliberately diverse/malformed fixtures (`docker/emails/`, `docker/emails-permanent/` — real-world corpus included) actually get exercised against parser bugs, instead of only against hand-picked synthetic cases; a real bug (crash on an unrecognized `Content-Transfer-Encoding`, and separately on truncated/malformed real-world messages) reached a user specifically because no test was driving the full corpus through the detail endpoint. Because of this, endpoint code that processes message content (bodies, headers, MIME structure) should be written to degrade gracefully on malformed input — return partial/empty results — rather than fail the request; see `parseEmailBody` in `emails.go` for the pattern (never returns an error).
- After manually running the Go server for testing (`go run ./cmd/server`), always verify it's actually stopped afterward — `go run` execs a separate child binary whose command line won't match `pkill -f "go run ..."`; check the listening port (`ss -ltnp | grep <port>`) and kill that PID directly.

## Test-data tooling (docker/generate-emails/, docker/populate-mailbox/)

Goal: give the future API's IMAP parser a diverse, deliberately-tricky set of `.eml` fixtures (charsets, transfer encodings, multipart shapes, and malformed headers/BODYSTRUCTURE), without needing large bodies or attachments. Each folder has its own README.md with usage details.

- `generate-emails/generate_synthetic_emails.py` — hand-built cases covering both valid diversity and deliberate malformation. Add new edge cases here as the parser's error-handling requirements become clearer.
- `generate-emails/fetch_corpus_samples.py` — pulls a small, size-capped sample from the SpamAssassin public corpus for organic real-world diversity.
- `populate-mailbox/populate_mailbox.py` — always fully wipes the test user's mailbox (all folders except INBOX, INBOX emptied) before repopulating from two sources: `emails/<folder>/*.eml` (per-folder) and `emails-permanent/*.eml` (flat, always to INBOX) — delivering each file's raw bytes (no reparsing/re-serializing client-side) via LMTP rather than IMAP `APPEND` — this is deliberate: real delivery is what adds diverse (including malformed-adjacent) headers like `Return-Path`/`Delivered-To`/`Received` on top of the fixture, which IMAP APPEND wouldn't. Folder targeting relies on Dovecot's `+detail` routing (see `zz-local-lmtp.conf` above). The wipe only ever touches the Dovecot mailbox, never the local `.eml` files — `emails-permanent/`'s files are untouched and simply get redelivered on the next run. `MAILBOX_USER`/`MAILBOX_PASSWORD` are constants at the top of the script, deliberately independent from `docker/.env` — if you change `DOVECOT_MAILBOX_PASSWORD`, update `MAILBOX_PASSWORD` here too, since Dovecot's default auth uses one shared password for every username.

## Gaps vs. the legacy API (webmail-api)

There's a legacy Ruby/Rails API at `/home/fabio/projects/webmail-api` (sibling project, not part of this repo) that this API is gradually replacing — full endpoint list in its `ENDPOINTS.md`. The goal is functional parity where in-scope (not contract parity — params/response shapes are being redesigned from scratch here, see `api/README.md`). Below is what's already covered vs. still missing, current as of 2026-09-08 — re-check `ENDPOINTS.md` there and this repo's `api/README.md` before trusting this list, since both move.

**Already covered (functionally, not contract-for-contract):** listing folders + unread counts (`list_folder`/`detail_folder` → `GET /folders`, `GET /folders/{pasta}`), deleting a folder (`delete_folder` → `DELETE /folders/{pasta}`), creating a folder (`create_folder` → `POST /folders/{pasta}` — note: legacy validates the name client-side (letters/numbers only, max 15 chars); this API just forwards to IMAP `CREATE` and translates the server's own error, see the validation-approach decision below), renaming a folder (`rename_folder` → `PATCH /folders/{pasta}`, body `{"name": "..."}`), emptying a folder (`empty_folder` → `DELETE /folders/{pasta}/emails` with no body), deleting a specific set of messages (`delete_mail` → `DELETE /folders/{pasta}/emails` with `{"uids": [...]}` body — bulk via a uids array, not one-message-per-call, per explicit user instruction: "bulk sempre com body passando um array"), moving messages (`move_mail` → `PATCH /folders/{pasta}/emails/move`, body `{"uids": [...], "destinationFolder": "..."}`), marking read/unread, starred/unstarred, answered and forwarded in bulk (`action_mail`'s `read`/`unread`/`starred`/`unstarred` ops plus `\Answered`/`$Forwarded` — legacy has no direct equivalent for those two, added proactively per explicit user request → `PATCH /folders/{pasta}/emails/flags`, body `{"uids": [...], "read": true|false, "starred": true|false, "answered": true|false, "forwarded": true|false}`, every field optional and independent, via the shared `storeFlag` helper in `emails.go` — see the endpoint-split decision below: flags and move used to be one combined `PATCH /folders/{pasta}/emails` endpoint (with a `to` field alongside `read`/`starred`), split into two dedicated endpoints per explicit user request), paginated message listing (`v2 list_mail` → `GET /folders/{pasta}/emails` — note: legacy supports `order_by` of `subject` or `date`, this API only sorts by date so far), full message read (`read_mail` → `GET /folders/{pasta}/emails/{uid}` — note: legacy also detects calendar/`.ics` invites via `has_calendar`, not implemented here), structured search in one or all folders (`v2 search_mail` → `GET /emails/search`, see `api/README.md` for the filter set and `internal/httpapi/search.go` for the all-folder goroutine fan-out — `unread_search`/`flagged_search` didn't get dedicated endpoints since they're just this same search with `folder=INBOX` + `unread`/`starred`), attachment download (`GET /v1/imap/attachment` → `GET /folders/{pasta}/emails/{uid}/attachments/{attachmentId}` — note: legacy addresses the attachment by `cid`/`filename` query params, this API instead returns a ready-to-use `attachmentLink` per attachment in `GET /folders/{pasta}/emails/{uid}`, see `internal/httpapi/attachments.go`), a basic liveness check (`probe/status` → `GET /health`, process-alive only — see below, legacy's `probe/check_all`, which also checks MySQL/IMAP/SMTP connectivity, has no equivalent here), raw message source (no direct legacy equivalent — `GET /folders/{pasta}/emails/{uid}/raw`, `message/rfc822`, doesn't mark `\Seen`), account storage quota (the IMAP-sourced half of `/v1/user/info` → `GET /account`, `internal/httpapi/account.go` — `GETQUOTAROOT` on INBOX, converted from the protocol's native KiB to bytes; no `mailbox_status` field, since it's vestigial here — auth failure already surfaces as 401 before any body is built, so it would never vary; `quotaTotal`/`quotaUsed` come back `null`, not `0`, when the account/server has no `STORAGE` quota — true today against the local Dovecot, which has the quota plugin disabled, confirmed via `GETQUOTAROOT` returning `BAD ... Unknown command`).

**Design decisions behind the write endpoints (`internal/httpapi/folders.go`, `internal/httpapi/emails.go`), settled with the user before implementing:**
- Resource-oriented URLs, not verb/RPC-named ones like legacy's `/action_mail` — `POST`/`PATCH`/`DELETE` on `/folders/{pasta}` and `/folders/{pasta}/emails`. `PATCH /folders/{pasta}/emails/flags` and `PATCH /folders/{pasta}/emails/move` are the one exception: flags and move started as a single combined `PATCH /folders/{pasta}/emails` (body carrying `read`/`starred`/`to` together), then got split into these two dedicated sub-paths per explicit user request — motivated by wanting the flags side to grow into a generic, self-contained "set any flag" endpoint (now `read`/`starred`/`answered`/`forwarded`, all independent optional `*bool` fields, see `patchEmailFlagsRequest` in `emails.go`) without move's `destinationFolder` cluttering that shape.
- Bulk message operations (move/delete/flags) always take a `uids` array in the request body — never one-`{uid}`-per-call, per explicit user instruction: "bulk sempre com body passando um array".
- Folder name validation: none client-side — the API trusts the IMAP server's own errors (e.g. `ALREADYEXISTS` → 409) rather than reimplementing legacy's provider-specific rules (15-char limit, alnum-only).
- The "trash folder" `DELETE /folders/{pasta}/emails` moves messages to is a **hardcoded** constant (`trashFolderName = "Trash"` in `emails.go`) — not discovered via IMAP SPECIAL-USE (`\Trash`, RFC 6154) and not a request parameter. Doesn't work for accounts whose real trash folder has a different name (e.g. "Lixeira", "Deleted Items"). Empirically, the local Dovecot (from the base `dovecot/dovecot` image's own default config, not anything in `docker/dovecot/conf.d/`) already treats "Trash" as a special auto-provisioned mailbox — a `MOVE` to it silently (re-)creates it even if just deleted, which is why there's no integration test for the "trash folder missing" error path (`errTrashFolderMissing`, 404) — that mechanism is exercised instead via `TestMoveEmails_DestinationNotFound`, which moves to an ordinary nonexistent folder name Dovecot has no special knowledge of.

**Out of scope by design, not a gap:** `send_mail` (SMTP — decided out of scope), `/v1/user/signature` and `/v1/user/sender_name` and the `from_name`/`external_accounts` fields of `/v1/user/info` (DB-backed user preferences — this API keeps no state of its own), the spam-sender-blocking side effect of `action_mail`'s `spam`/`not_spam` operations (`idtPerson`/`emails` params, DB-backed).
